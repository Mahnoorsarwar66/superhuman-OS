# Implementation and boundaries

The new `superhuman.teamhub` package adds owner workspace metadata, channels, topic threads, bounded rounds, exact dialogue-step references, source links and work cards to the existing project SQLite database. It does not replace the task, milestone, evidence or budget engines.

The hosted worker reconciles one discussion round at a time under its existing global lock. It queues ordinary dialogue turns for a real employee. A lead planning reply uses a strict extra requests field; at most two unique rostered non-lead participants may be requested. Specialists reply sequentially, then the lead integrates actual saved content. A direct reply uses the usual schema. Failure/interruption stops the round without automatic replay. Explicit fresh attempts retain the original history and may incur cost.

Project-channel membership is owner-confirmed, bounded by current milestone roster and project sharing. Both prompt construction and pre-commit validation check current context. Normal Storage retrieval is additionally filtered for all channel participants, preventing a private source available to one author from entering shared retrieval. Explicit document links pin source version/hash and independently check current access and health. This protects retrieval boundaries; it cannot establish semantic truth or guarantee that an owner never types private information in a shared project thread.

Work cards are exact, versioned records linked to real dialogue proposals. The Twin independently reviews only eligible routine internal cards under its existing role. Model approval is not a deterministic proof of safety or usefulness. Software enforces risk/classification floors, owner gates, no self-review, duplicate prevention, two review attempts, current project controls, current card snapshot, existing task/milestone constraints and existing tool permissions. Model responses and execution outputs remain reviewable. Automatic review is opt-in per channel; a revised card is not automatically resubmitted forever.

Managed project cards must specify an existing working milestone and permitted contributor. They create ordinary milestone assignments; reviews and exact-version packet approval remain in the existing pipeline. They do not alter milestone criteria, dependencies, owner approvals, project scope or permitted tools. Generic project cards use the existing Twin queue and task scheduler. An authorized card can still wait for the initial project interview, department goal, budget or other gates; its UI links to the actual assignment and reason.

Read state is explicit and based on actual stored reply signatures/counts. There is no invented online presence, unread number or external notification channel. Existing histories are baselined at initial migration. UI GETs read data without starting replies or marking content read; first-use schema setup is additive. Direct-chat creation/selection, channel creation, sends, source links and approvals are CSRF-protected POSTs under the existing single-owner authenticated boundary.

The interface reuses local fictional employee portraits and forest-green styling, with quiet message surfaces. Employee overview, focused conversation, optional context disclosures and source-backed work events provide the balance of communication and management requested. Existing list bookmarks and controls continue working. There is no external deployment in this deliverable.
